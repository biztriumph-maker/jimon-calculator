# VISUAL IMPLEMENTATION PLAYBOOK
## Как переносить утверждённый визуал из ChatGPT / макета в реальный сайт или приложение без потери качества и без бесконечных переделок

Version: 1.0  
Purpose: reusable workflow for any future project  
Audience: владелец проекта + ChatGPT + Codex / разработчик  
Core principle: **сначала выбираем архитектурно правильный способ переноса визуала, только потом пишем код.**

---

# 1. Главная идея

Утверждённый визуал — это **источник истины**, а не источник вдохновения.

Если картинка утверждена, разработчик / Codex НЕ должен:
- придумывать новую композицию;
- менять фон;
- менять расположение блоков;
- заменять иконки «похожими»;
- добавлять свои элементы;
- менять цвета «на вкус»;
- менять пропорции без отдельного согласования.

Любое отклонение от approved visual считается дефектом, пока владелец отдельно не утвердил изменение.

---

# 2. Первый вопрос перед началом: что именно мы переносим?

Перед кодом классифицировать экран.

## Тип A — почти статичный визуальный экран

Примеры:
- приветственный экран;
- hero / landing screen;
- onboarding screen с 1–2 кликабельными зонами;
- экран, где всё визуально утверждено и почти ничего не меняется.

### Лучший способ
Использовать **единый approved visual как raster / image layer**, а интерактивность добавить поверх прозрачными HTML controls.

Это предпочтительно, если:
- визуал сложный;
- фон художественный;
- много декоративных деталей;
- экран должен совпасть почти 1:1;
- нет большого количества динамического текста.

---

## Тип B — интерактивный / динамический экран

Примеры:
- каталог;
- фильтры;
- карточки товаров;
- расчёт;
- план покупок;
- форма;
- modal;
- список заказов;
- экран скидок;
- таблицы;
- динамические значения.

### Лучший способ
Переносить визуал в **настоящий HTML/CSS / React**, а approved visual использовать как reference.

На таких экранах нельзя делать всё одной картинкой, потому что:
- текст должен быть резким;
- данные меняются;
- элементы должны реагировать на состояние;
- нужна доступность;
- нужны responsive states.

---

# 3. Критическое решение №1: IMAGE LOCK или HTML REBUILD

До начала работы выбрать только один режим.

## IMAGE LOCK

Использовать, если экран статичный или почти статичный.

Схема:

`approved visual → clean reference → 2x runtime image → transparent hit areas`

Плюсы:
- самое точное визуальное совпадение;
- быстрый результат;
- минимум CSS;
- минимальный риск, что Codex «переизобретёт дизайн».

Минусы:
- текст внутри raster будет менее резким, чем HTML;
- нельзя удобно менять динамические значения;
- нужен качественный исходник.

---

## HTML REBUILD

Использовать, если экран динамический.

Схема:

`approved visual → visual contract → assets → HTML/CSS → screenshot → overlay`

Плюсы:
- настоящий responsive;
- резкий текст;
- доступность;
- динамические данные;
- удобная поддержка.

Минусы:
- требует больше времени;
- выше риск расхождений;
- нужен точный UI contract.

---

# 4. Чего нельзя делать

## Неудачный путь №1
Разрезать сложный approved hero на много случайных фрагментов и потом «собирать» его CSS-ом.

Это часто приводит к:
- чёрным полосам;
- обрезанным листьям;
- несовпадающим фонам;
- белым прямоугольникам;
- неправильным z-index;
- разъехавшимся краям.

### Правило
Если сцена сложная и статичная — лучше один clean approved visual.

---

## Неудачный путь №2
Пытаться лечить плохой crop:
- `scale(1.2)`;
- `mask-image`;
- `blur`;
- `gradient`;
- oversize;
- отрицательные margin;
- случайный `clip-path`.

Если источник плохой — сначала исправить SOURCE ASSET.

---

## Неудачный путь №3
Просить Codex:
> «Сделай похоже на эту картинку»

Это слишком свободно.

Нужно:
> «Это утверждённый визуальный эталон. Не изменять композицию. Следовать contract.»

---

## Неудачный путь №4
Делать 5–10 visual passes подряд.

Если после 1–2 проходов метод не даёт результата —
**менять архитектуру реализации**, а не продолжать латать.

---

# 5. Как подготовить approved visual

## Шаг 1 — сохранить исходный утверждённый файл

Пример:

`01_APPROVED_UI.png`

Он должен быть неизменяемым source of truth.

---

## Шаг 2 — сделать нормализованный reference

Если исходник содержит:
- корпус телефона;
- status bar;
- рамку;
- подписи вокруг;
- background презентации;

вырезать только content area.

Пример:

`SCREEN_HOME_REFERENCE_390.png`

---

## Шаг 3 — убрать технические артефакты

Удалить:
- куски рамки телефона;
- чёрные края;
- лишние 1–6 px;
- случайные линии;
- чужие элементы презентации.

Важно:
не менять сам дизайн.

---

## Шаг 4 — подготовить 2x runtime

Если control width = 390 px:

runtime raster желательно:
- 780 px wide;
- 2x density.

Пример:

`SCREEN_HOME_REFERENCE_2X.png`

Это помогает на Retina / HiDPI.

---

# 6. Контрольный viewport

Для каждого mobile-first проекта заранее выбрать control viewport.

Рекомендуемый стандарт:

`390 × 844`

Дополнительно проверять:
- 360 × 800
- 375 × 812
- 390 × 844
- 393 × 852
- 412 × 915
- 430 × 932

---

# 7. Responsive strategy для IMAGE LOCK

Лучший базовый вариант:

```css
.screen-shell {
  position: relative;
  width: 100%;
  max-width: 430px;
  margin-inline: auto;
}

.screen-reference {
  display: block;
  width: 100%;
  height: auto;
}
```

Не использовать без необходимости:
- `scaleY`;
- `object-fit: fill`;
- независимую высоту;
- width, вычисляемую от `vh/svh`.

---

# 8. Если экран должен помещаться целиком

Сначала:
1. убрать лишние margin/padding;
2. убрать min-height;
3. убрать footer spacer;
4. убрать лишний safe-area;
5. проверить app-shell.

Только потом уменьшать весь визуал пропорционально.

Никогда не сплющивать изображение по вертикали.

---

# 9. Прозрачные hit-area кнопки

Если экран — raster reference, но нужно сохранить интерактивность:

```css
.hit-area {
  position: absolute;
  background: transparent;
  border: 0;
  box-shadow: none;
}
```

Координаты задавать в процентах относительно reference.

Пример:

```text
left: 3.08%
top: 46.27%
width: 93.85%
height: 17.29%
```

Плюсы:
- responsive;
- зона клика масштабируется вместе с картинкой;
- логика остаётся настоящей.

---

# 10. Когда raster НЕ использовать

Не использовать full-screen raster, если:
- текст меняется;
- цены меняются;
- скидка меняется;
- количество товаров динамическое;
- форма редактируемая;
- пользователь выбирает несколько состояний;
- нужен поиск;
- нужен каталог;
- нужны accessibility semantics.

Там нужен настоящий UI.

---

# 11. Visual Contract для HTML REBUILD

До Codex обязательно зафиксировать:

- viewport;
- координаты;
- grid;
- padding;
- gap;
- размеры карточек;
- radius;
- shadow;
- typography;
- colors;
- icon size;
- image size;
- states;
- responsive rules.

Файл:

`XX_UI_VISUAL_CONTRACT.md`

---

# 12. Assets Manifest

Отдельно создать:

`XX_ASSET_MANIFEST.md`

В нём:

| Asset | Source | Exact? | Runtime path |
|---|---|---|---|
| Logo | approved reference | YES | ... |
| Hero | approved reference | YES | ... |
| Icon 1 | SVG | YES | ... |

Codex НЕ имеет права самостоятельно выбирать другой asset.

---

# 13. Как писать задачу Codex

Структура хорошего prompt:

1. Scope.
2. Source of truth.
3. Что можно менять.
4. Что нельзя менять.
5. Exact text.
6. Exact states.
7. Screenshot protocol.
8. Build/tests.
9. Stop conditions.
10. No commit / commit rule.

---

# 14. Универсальный prompt для IMAGE LOCK

```text
Это утверждённый визуальный эталон, а не пример.

Работай только с экраном X.

Используй approved reference image как единый visual layer.
Не реконструируй logo/background/illustration по частям.
Не меняй композицию.

Сохрани интерактивность через прозрачные HTML hit-area controls.

Не меняй бизнес-логику.
Не переходи к другим экранам.

После реализации:
- screenshot 390×844;
- responsive check;
- build/tests;
- stop.
```

---

# 15. Универсальный prompt для HTML REBUILD

```text
Это утверждённый визуальный эталон.

Перед изменением прочитай:
- VISUAL_CONTRACT
- ASSET_MANIFEST
- APPROVED_REFERENCE

Не придумывай композицию.
Не меняй тексты.
Не меняй layout без отдельного разрешения.

Реализуй только экран X.

После реализации:
- screenshot 390×844;
- overlay;
- diff;
- responsive;
- build/tests;
- stop.
```

---

# 16. Screenshot protocol

Control:

```text
viewport: 390×844
DPR: 1
zoom: 100%
scrollY: 0
```

Имя:

`screen_390_actual.png`

---

# 17. Overlay / diff

Использовать только как диагностический инструмент.

Не делать pixel diff самоцелью.

Приоритет:

1. визуально правильно;
2. функционально правильно;
3. responsive;
4. diff.

Если глаз видит дефект, MAE=0.7 не спасает экран.

---

# 18. Когда остановиться

Экран считается готовым, если:

- владелец визуально согласен;
- нет артефактов;
- нет scroll, если его не должно быть;
- нет horizontal scroll;
- клики работают;
- build проходит;
- tests проходят;
- responsive проверен.

После этого:

`SCREEN_VISUAL_LOCKED.md`

И экран больше не трогать.

---

# 19. Правило Freeze

После утверждения:

- создать lock-файл;
- commit;
- новый Codex chat;
- следующий экран.

Нельзя продолжать редактировать предыдущий экран в рамках новой задачи.

---

# 20. Экономия Codex лимита

Очень важно.

## ChatGPT делает:
- анализ;
- сравнение картинок;
- выбор архитектуры;
- подготовку reference;
- visual contract;
- asset manifest;
- готовый prompt.

## Codex делает:
- одно внедрение;
- build/tests;
- screenshot;
- один correction pass максимум.

Не использовать Codex как:
- визуального консультанта;
- генератор вариантов;
- место для бесконечных экспериментов.

---

# 21. Правило 1+1

На один экран:

- 1 implementation pass;
- максимум 1 correction pass.

Если не получилось —
не третий correction pass,
а пересмотр архитектуры.

---

# 22. Git workflow

Перед началом:
- clean tree;
- baseline commit.

После screen freeze:
- cleanup временных assets;
- build/tests;
- final screenshot;
- commit;
- no push без отдельной команды.

---

# 24. Ошибки, которые нельзя повторять

1. Собирать сложный hero из 5–6 crops без необходимости.
2. Использовать crop с остатками рамки телефона.
3. Маскировать плохой source CSS-ом.
4. Гонять build/tests после каждой мелочи.
5. Делать overlay после каждого пикселя.
6. Разрешать Codex «улучшать» дизайн.
7. Не замораживать готовые экраны.
8. Использовать один перегруженный Codex chat на весь проект.
9. Делать новый screen pass без clean git.
10. Коммитить временные screenshots/assets.

---

# 25. Быстрый decision tree

## Вопрос 1
Экран статичный?

### Да
IMAGE LOCK.

### Нет
HTML REBUILD.

---

## Вопрос 2
Визуал сложный?

### Да
Не режем без необходимости.
Используем единый approved reference.

### Нет
Можно HTML/CSS.

---

## Вопрос 3
Текст динамический?

### Да
HTML.

### Нет
Raster допустим.

---

## Вопрос 4
После первого pass визуал плохой?

### Незначительно
1 correction pass.

### Сильно
STOP.
Меняем архитектуру.

---

# 26. Финальный стандарт работы

Для каждого нового экрана:

```text
APPROVED VISUAL
↓
CLASSIFY SCREEN
↓
CHOOSE ARCHITECTURE
↓
PREPARE REFERENCE / ASSETS
↓
WRITE CONTRACT
↓
ONE CODEX IMPLEMENTATION PASS
↓
SCREENSHOT
↓
ONE CORRECTION MAX
↓
FREEZE
↓
COMMIT
↓
NEW CHAT
```

---

# 27. Ключевая формула

**Не пытаться кодом воспроизвести то, что уже идеально утверждено как статичный visual.  
Не превращать в картинку то, что должно быть настоящим интерактивным UI.**

Это главный принцип всего workflow.
